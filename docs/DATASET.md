# Schema-pair dataset

This dataset uses target identifier metadata from the Dr.Spider
`DB_schema_synonym` and `DB_schema_abbreviation` perturbation sets. It supports
three methods on the same held-out data: the SBERT matcher, the few-shot LLM
baseline, and the oracle/gold-mapping pipeline.

It contains two evaluation groups:

- `standard`: the 182 Dr.Spider synonym/abbreviation pairs.
- `challenge`: 20 additional pairs with curated semantic table renaming and
  broader column renaming. These isolate harder naming changes while retaining
  exactly the same data, types, PKs, FKs, and SQL dialect.

## Build

Selectively extract `Spider-dev`, `DB_schema_synonym`, and
`DB_schema_abbreviation` from the Dr.Spider archive into
`work/raw_drspider/`. Then build a fresh dataset with:

```bash
python scripts/build_pair_dataset.py \
  --raw-root work/raw_drspider \
  --output-root data \
  --seed 4705
```

The builder refuses to overwrite an existing `data/` directory.

## Layout

```text
data/
├── splits.json
└── pairs/
    └── concert_singer__syn_v0/
        ├── db_A.sqlite
        ├── db_B.sqlite
        ├── schema_A.json
        ├── schema_B.json
        ├── gold_mapping.json
        └── queries.jsonl
```

`syn` means schema-synonym perturbation and `abbr` means schema-abbreviation
perturbation. Including the perturbation type prevents pair-ID collisions.
Challenge pairs use names such as `concert_singer__challenge_v0`.

`schema_A.json` keeps the original Spider order. `schema_B.json` shuffles table
and column presentation order deterministically. The SQLite database itself is
not reordered; models should consume the JSON schema representation.

`gold_mapping.json` contains the complete reusable mapping, including unchanged
identifiers. Dr.Spider's two selected perturbations rename columns but do not
rename tables, so table mappings are identity mappings. Do not fabricate table
renames for this benchmark.

Challenge mappings rename every ordinary table and most columns with curated
semantic aliases. SQLite's internal `sqlite_sequence` table is not renamed.
The challenge group reuses the same 20 Spider-dev base databases, so it raises
renaming difficulty but does not increase independent schema diversity. Report
standard and challenge results separately and macro-average by base database.

`gold_q_B` is generated by `rewrite.rewrite(q_A, gold_mapping)`. Evaluation
must call the same function with a predicted mapping. This prevents data
generation and evaluation from silently using different SQL rewriting logic.

The SQLite files are hard-linked when the filesystem supports it, which avoids
duplicating hundreds of megabytes. Treat them as read-only: modifying a hard
link modifies every path that refers to the same database inode.

`db_B.sqlite` is deliberately generated by copying `db_A.sqlite` and applying
only the gold table/column renames. We do not copy Dr.Spider's provided post
SQLite database because a data audit found content differences in a small
number of rows (for example whitespace or text changes). Generating B from A
keeps the data, keys, relationships, and SQL dialect fixed, so schema naming is
the isolated experimental variable.

## Query labels

Every `queries.jsonl` row has exactly these fields:

```json
{"qid":"concert_singer__syn_v0__q0002","q_A":"...","gold_q_B":"...","is_join":false,"level":"L2"}
```

- `is_join` is true when the parsed Spider SQL contains a query block with two
  or more source tables.
- `L1`: the query references zero renamed schema elements.
- `L2`: the query references exactly one renamed schema element.
- `L3`: the query references two or more renamed schema elements.

The level counts distinct referenced table/column identifiers, not the number
of textual occurrences.

## Split policy

`splits.json` assigns entire original Spider databases to train/dev/test using a
70/15/15 split and seed 4705. All synonym and abbreviation variants of the same
base database remain in the same split. Never resplit individual queries or
pair folders, because that would leak the same schema across train and test.

Use the splits as follows:

- SBERT: train on `train`, choose hyperparameters on `dev`, report once on
  `test`.
- Few-shot LLM: use demonstrations only from `train`; tune prompt choices on
  `dev`; evaluate the frozen prompt on `test`.
- Oracle: feed `test` gold mappings through the same SQL rewriter to measure the
  pipeline ceiling.

## Validate

Structural checks and SQLite integrity checks:

```bash
python scripts/validate_pair_dataset.py --data-root data
```

Full validation also executes every source/target query and compares result
multisets:

```bash
python scripts/validate_pair_dataset.py --data-root data --execute
```

The machine-readable result is written to
`outputs/dataset_validation.json`.

Challenge-generation audit statistics are stored in
`outputs/challenge_data_audit.json`. The generator is:

```bash
python scripts/build_challenge_dataset.py \
  --raw-root work/raw_drspider \
  --data-root data
```
