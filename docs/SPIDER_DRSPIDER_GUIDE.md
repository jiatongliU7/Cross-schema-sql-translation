# Spider and Dr.Spider experiment guide

This project prepares Spider-derived schema pairs and audits Dr.Spider schema perturbations. The datasets and model weights are not included. The data adapters have been tested with synthetic fixtures, not the official distributions in this environment. Inspect each official dataset release before running a large experiment.

## Obtain the data

- [Spider project and dataset](https://github.com/taoyds/spider), [Spider download page](https://yale-lily.github.io/spider): obtain the SQLite databases, `tables.json`, and the train/dev query JSON files.
- [Dr.Spider dataset and preprocessing](https://github.com/awslabs/diagnostic-robustness-text-to-sql): obtain and extract the official archive and run its preprocessing instructions. Use the `DB_schema_synonym` and `DB_schema_abbreviation` perturbations for schema renaming.

The official Dr.Spider preprocessing script copies pre-perturbation databases and tables from Spider dev. All example paths below are placeholders; inspect your extracted data first.

## Prevent database leakage

Dr.Spider is based on Spider's development set. Split by original database before generating variants: all versions of the same database belong to one split. If Dr.Spider is the final test set, exclude its original databases from training and tuning as well. Ensure that examples and all transformations remain in the same split.

`check-splits` takes three JSON arrays of objects with a `db_id` field:

```bash
python -m sqltranslate.cli check-splits --train train_manifest.json --dev dev_manifest.json --test test_manifest.json
```

Checking IDs cannot detect equivalent databases with different IDs; inspect provenance separately.

## Prepare a Spider pair

```bash
python -m sqltranslate.cli prepare-spider \
  <spider/database/DB_ID/DB_ID.sqlite> <spider/train_spider.json> \
  --outdir experiments/spider_db --difficulty easy --seed 42
```

This makes a SQLite backup, renames tables and columns, and writes `target.sqlite`, `gold.json`, `queries.json`, and `manifest.json`. The gold mapping is generated by the rename operation; it is not an existing cross-database mapping supplied by Spider. The database ID is inferred from the SQLite filename. The built-in difficulty options are simple heuristics, not validated difficulty levels. Audit generated names for semantic accuracy, ambiguity, and shortcuts.

## Prepare a Dr.Spider candidate mapping

```bash
python -m sqltranslate.cli prepare-dr \
  --pre-tables <DB_schema_synonym/tables_pre_perturbation.json> \
  --post-tables <DB_schema_synonym/tables_post_perturbation.json> \
  --source <databases_pre_perturbation/DB_ID/DB_ID.sqlite> \
  --target <databases_post_perturbation/DB_ID/DB_ID.sqlite> \
  --db-id DB_ID --outdir experiments/dr_db
```

When pre/post question files have the fields `db_id`, `q_id_spider_dev`, and `query`, pass both `--pre-questions <file>` and `--post-questions <file>` to produce paired queries. Check the actual release format if these fields differ.

The adapter proposes correspondences by aligned positions only after checking schema metadata, names against SQLite, mapped row contents, and declared SQLite FKs. Inspect `candidate_mapping.json` and its audit. **The result is a candidate, not verified or official ground truth.** Empty tables, equal-valued columns, or graph symmetries can make an incorrect candidate pass checks. Manually review, correct, and save a separate `reviewed_gold.json`. Investigate any content or FK mismatch before comparing query results across databases. `DBcontent_equivalence` is outside this rename-only adapter.

## Evaluate column retrieval

```bash
pip install -r requirements-neural.txt
python -m sqltranslate.cli retrieval-eval <source.sqlite> <target.sqlite> <reviewed_gold.json> --method lexical --top-k 3 --out lexical.json
python -m sqltranslate.cli retrieval-eval <source.sqlite> <target.sqlite> <reviewed_gold.json> --method sbert --top-k 3 --out pretrained.json
python -m sqltranslate.cli retrieval-eval <source.sqlite> <target.sqlite> <reviewed_gold.json> --method sbert --model models/schema-sbert --top-k 3 --out finetuned.json
python -m sqltranslate.cli retrieval-summary lexical.json pretrained.json finetuned.json --out evaluation.csv
```

Top-1 accuracy and Top-k recall are computed independently for each source column over all target columns, before assignment, explicit type scoring, or FK reranking. The JSON includes candidate ranks. SBERT input descriptions currently include type and PK/FK roles; an experiment withholding those features needs different descriptions. CSV rows summarize individual reports; calculate micro and macro aggregates explicitly when using multiple databases.

## Train on the training split only

Combine Spider training pair manifests into a JSON array, then run:

```bash
python -m sqltranslate.cli pairs train_manifest.json --out train_pairs.json
python -m sqltranslate.cli train train_pairs.json --out models/schema-sbert --epochs 1 --batch-size 8
```

The starter trainer uses cosine regression with randomly sampled negatives, not MultipleNegativesRankingLoss. Negatives can be false negatives and require review; tune only on development databases. Model training has not been executed in the current environment.

## Evaluate translated SQL

For a Spider-derived pair whose data correspondence is verified:

```bash
python -m sqltranslate.cli match <source.sqlite> <target.sqlite> --method lexical --out prediction.json
python -m sqltranslate.cli evaluate <source.sqlite> <target.sqlite> prediction.json --queries <queries.json> --gold <gold.json> --out report.json
```

For Dr.Spider paired queries:

```bash
python -m sqltranslate.cli paired-eval <source.sqlite> <target.sqlite> prediction.json experiments/dr_db/paired_queries.json --out paired_report.json
```

The paired report separates target-side comparison (generated SQL and official post SQL run on the same target database) from cross-database comparison (only meaningful when data correspond). Known errors in some official post-perturbation SQL have been [reported upstream](https://github.com/awslabs/diagnostic-robustness-text-to-sql/issues/1). Execution on one data instance cannot establish general semantic equivalence. Record errors and investigate empty results, duplicates, numeric precision, and ordering.
